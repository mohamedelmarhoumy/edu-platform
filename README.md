# Backend المنصة التعليمية

باك-إند حقيقي (Node.js + Express + PostgreSQL) يطبّق المرحلة الأولى من
كراسة المتطلبات: تسجيل دخول بـ OTP، ربط الجهاز، حماية تشغيل الفيديو عبر
VdoCipher بعلامة مائية ديناميكية، أكواد تفعيل، اختبارات إلكترونية،
ومبني منذ البداية ليدعم أكثر من معلّم (Multi-Teacher) لاحقاً.

## 1. التشغيل محلياً

```bash
cp .env.example .env      # أو استخدم .env الموجود بالفعل ومعبّأ بمفتاح VdoCipher
npm install
npm run migrate           # ينشئ كل الجداول في PostgreSQL
node src/db/seedTeacher.js "اسمك" "01xxxxxxxxx" "you@example.com" "كلمة_مرور_قوية"
npm run dev
```

الخادم يعمل افتراضياً على `http://localhost:4000`. جرّب `GET /health`.

> **مهم:** ملف `.env` المرفق يحتوي بالفعل على مفتاح VdoCipher السرّي الذي
> شاركته. بما أن هذا المفتاح مرّ عبر محادثة، **يُفضَّل توليد مفتاح جديد
> (Regenerate Secret Key) من لوحة تحكم VdoCipher بعد الانتهاء من التجربة**،
> ولا ترفع `.env` على GitHub أو أي مكان عام إطلاقاً (موجود بالفعل في
> `.gitignore`).

## 2. الهيكل

```
src/
  config/       اتصال قاعدة البيانات ومتغيرات البيئة
  db/           ملفات SQL للترحيل + سكربتات seed
  services/     VdoCipher, OTP, JWT — منطق معزول قابل لإعادة الاستخدام
  middleware/   التحقق من الهوية + تطبيق قاعدة "جهاز واحد لكل حساب"
  controllers/  منطق كل مسار (auth, courses, video, promo, quizzes, students, teachers)
  routes/       تجميع المسارات حسب الدور (auth / student / admin / superadmin)
```

## 3. كيف تعمل الحماية عملياً

1. المعلّم يرفع فيديو من لوحة التحكم → `POST /api/admin/lessons/:id/upload-credentials`
   يطلب من VdoCipher رابط رفع مباشر، والملف يُرفع من متصفح المعلّم مباشرة
   إلى تخزين VdoCipher (لا يمر على سيرفرنا).
2. عند تشغيل الطالب للفيديو → `POST /api/student/lessons/:id/playback`
   يتحقق الخادم من: الاشتراك فعّال؟ لم يتجاوز عدد المشاهدات المسموح؟
   لم تنتهِ صلاحية الوصول؟ ثم يطلب من VdoCipher توكن تشغيل صالح 5 دقائق
   فقط، مع تفعيل علامة مائية متحركة تحمل اسم ورقم هاتف الطالب.
3. "جهاز واحد لكل حساب": عند أول دخول يُسجَّل بصمة الجهاز
   (`device fingerprint` تُحسب في الواجهة الأمامية من خصائص الجهاز/المتصفح
   وتُرسل مع كل طلب حساس عبر الترويسة `x-device-fingerprint`)، وأي جهاز
   مختلف لاحقاً يُرفض حتى يفكّ المعلّم الربط يدوياً.
4. "جلسة واحدة نشطة": تسجيل دخول جديد يستبدل الجلسة القديمة في الجدول
   `student_sessions`، فيصبح توكن الجهاز الأول غير صالح لطلب Refresh لاحق.

## 4. دعم أكثر من معلّم (Multi-Teacher) مستقبلاً

كل جدول رئيسي (`courses`, `students`, `promo_codes`, `questions`...) يحمل
`teacher_id`. لإضافة معلّم جديد لاحقاً:

```
POST /api/superadmin/teachers   (يتطلب حساب دورك فيه superadmin)
```

بعدها كل بياناته (كورساته، طلابه، أكواده) معزولة تلقائياً عن بقية
المعلمين دون أي تعديل في المخطط. الخطوة التالية الطبيعية عند تفعيل هذا
فعلياً هي إما نطاق فرعي لكل معلّم (`teacher-slug.yourdomain.com`) أو شاشة
اختيار "المدرسة/المعلّم" عند تسجيل دخول الطالب.

## 5. ما لم يُبنَ بعد (تحتاج قرارك قبل الاستكمال)

- **الواجهة الأمامية (الموقع الفعلي):** الأرتيفاكت التفاعلي المُرسَل سابقاً
  يوضّح كل الشاشات (تسجيل دخول، مشاهدة، اختبار، لوحة تحكم) — الخطوة
  التالية هي استبدال بياناته الوهمية بنداءات فعلية لهذه الـ API.
- **بوابة الدفع (Paymob/Fawry):** لم تُربط بعد؛ حالياً التفعيل عبر أكواد
  Promo فقط، وهذا متوافق مع خطة المرحلة الأولى.
- **حساب/تكامل SMS حقيقي لإرسال الـ OTP:** حالياً الكود يُطبع في الـ log
  فقط للتجربة (راجع `services/otpService.js`).
- **نشر فعلي (Deployment):** يحتاج استضافة Node.js + PostgreSQL فعلية
  (مثل Railway/Render/VPS) — لم يُنشر هنا لأن بيئة العمل الحالية بلا
  اتصال إنترنت خارجي.

## 6. ملاحظة على توثيق VdoCipher

منطق `services/vdocipherService.js` مبني على واجهة VdoCipher العامة كما
هي موثّقة، لكن مزوّدي الفيديو يُحدّثون حقول الـ API من وقت لآخر — راجع
https://www.vdocipher.com/docs/api/ وتأكد من مطابقة أسماء الحقول (خصوصاً
معامل `annotate` الخاص بالعلامة المائية) قبل الاعتماد عليه في الإنتاج.
